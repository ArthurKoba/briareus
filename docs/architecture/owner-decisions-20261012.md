# Briareus — действующее решение владельца от 12.10.2026

**НОВОЕ ВЫБРАННОЕ РЕШЕНИЕ 12.10.2026:** [Rauthy + Cedar](identity-rauthy-cedar-20261012.md) заменяют самописную Human Identity/JWT и собственный движок правил. Python Control Panel API и имеющиеся Team/Project, Authorization, PostgreSQL и Valkey сохраняются. Старые пункты A/B/F о самописной регистрации, подписи и bootstrap остаются только переходными требованиями к *уже запущенному* legacy Identity до проверенного cutover; дальнейшая разработка должна идти по новому документу. Остальные правила безопасности, ресурсов и независимых сервисов действуют.

**Статус: выбранное ТЗ.** Это предметное решение заменяет противоречащие ему прежние ENV-1, PACKAGING-V1, C2-Gateway и инструкции о раздельной папке deploy. История этих решений не является действующей нормой. Для интерфейсов Team/Project, не затронутых настоящим решением, сохраняются текущие продуктовые инварианты из target-project-platform.md. Приоритет: последняя явная команда владельца, затем этот документ, затем код/конфигурация по фактическому состоянию. Нельзя объявлять старый вывод оркестратора согласием владельца без прямого подтверждения.

## A. Первый суперпользователь, регистрация, вход

1. На старте Identity проверяет **фактическое число User с ролью superuser** в своей устойчивой базе. Если меньше одного, Identity выпускает системное приглашение регистрации и выводит полную ссылку с ключом в **startup logs Identity**. Это прямо выбранная владельцем штатная операторская выдача. Не требовать предварительно настроенного AF_UNIX оператора или отдельного bootstrap C2 ради этой задачи.
2. Если superuser уже есть (count >= 1), **ничего системного в логах не выдавать** — ни для обычных пользователей, ни на рестарте, ни в порядке резервного приглашения. Новые ссылки для обычных User выдаёт существующий superuser через собственный аутентифицированный интерфейс. Логика «печатать системное приглашение при каждом рестарте после bootstrap» УДАЛЕНА.
3. Если позже superuser действительно не осталось (count < 1), тот же сценарий при очередном старте снова позволяет первичное восстановление через системную ссылку в startup logs. Решение основано на числе superuser, а не на флаге «bootstrap уже однажды завершён». Не предполагать отдельно «только активных» без продуктового решения: роль superuser — точный критерий владельца. Сосуществование запрета удалить последнего superuser и восстановления при count=0 не конфликт: восстановление покрывает реально возникшую пустую роль.
4. Только один одновременный зарегистрировавшийся через первоначальное системное приглашение может получить роль superuser: транзакция/блокировка в Identity не допускает второго первого пользователя. Системный ключ ограничен назначением регистрации, не служит JWT/MCP credential; повторное использование отклоняется. Пока superuser нет, повторный старт не размножает действующие приглашения; допускается управляемое переиздание с отзывом старого, если невозможно восстановить действующий токен из защищённого хранения. Не реализовывать дополнительные механизмы без необходимости.
5. Startup logs — явное исключение из общего запрета журналировать секреты: **только системная ссылка в операторском startup-логе Identity при count < 1**. Никогда не копировать её в публичную HTTP-выдачу, Gateway analytics, логи вызовов MCP, трассировки, метрики, отчёты агентов или ответы инструментов. Агенты не раскрывают значения ключей. Проверить маршрутизацию OTLP так, чтобы этот исключительный лог не оказался доступен более широкой аудитории, чем действительный операторский просмотр. Не заменять согласованные startup logs Unix-сокетом.

## B. Подпись Identity и хранение настроек

- JWT для Human User подписывает **Identity**. Название ADMIN_JWT_SIGNING_KEY для нового Identity неверно, его не возвращать и не навязывать Backend. Точное уже обсуждаемое с Backend название/формат Identity signing key берутся из согласованного владельцем Identity-контура; без проверки не создавать параллельные имена или алиасы.
- Ключ подписи **постоянный между рестартами**. Временная генерация Ed25519PrivateKey.generate() на каждом запуске, уничтожающая все пользовательские сессии, должна быть заменена устойчивым операторским ключом соответствующего формата; не мигрировать на другой алгоритм JWT без причины. Подпись и проверка, смена ключа и JTI относятся Identity, не Gateway. Отсутствие необходимого реального ключа сообщать один раз как конкретный инфраструктурный вход, без фиктивного выпуска сессий.
- Секретные значения не записываются в Git, Dockerfile, Compose, Docker image или открытые Application variables. Доставка в runtime только как защищённая ссылка на одобренную Shared-переменную соответствующего scope. Не читать/печатать plaintext разрешённым агентам.
- **Team Shared**: общие между многочисленными проектами TZ и телеметрия (OTLP endpoint и защищённые credentials/параметры, если используются). **Environment Shared**: PostgreSQL/Valkey и окружение-зависимые secrets, в том числе Identity signing key, если он выделен для этого environment; принимать конкретные существующие scope/имена, не переносить их ради красоты. Project Shared допустим лишь для действительно проектно-специфичного значения по отдельному решению, не универсален для всех секретов.
- Фраза из старого ENV-1 «все секреты только Project Shared» и запрет Environment Shared **отменены**. Пометка owner-approved при старых требованиях без явного согласия не является доказательством одобрения.

## C. Сервисы, Control Panel, Gateway и Docker layout

- Независимые **platform/domain services**: Identity (пользователи/вход), Authorization (права и Access), Platform Control (Project/Team), Resource Catalog (ресурсы). Отдельные **infrastructure services** и внешние **Hands/MCP services** (Files, Terminal, Web, SVC, Infrastructure, Reverse и последующие). У каждого свои API, рабочая папка, сборка, контейнер, независимый релиз и жизненный цикл.
- Control Panel API — тонкий управляющий BFF, через внутренний HTTP общается с API соответствующего доменного сервиса, не владеет чужими таблицами, процессами и паролями. Control Panel UI — отдельный фронтенд. Их изменения не перезапускают Identity или Hands. Rename Admin API/UI выполняется поэтапно без потери рабочего публичного пути и реального UUID/данных приложения.
- Gateway — максимально тонкий маршрутизатор/stream-proxy и точка телеметрии. Проксирует public/Panel UI, весь /api/* к Control Panel API, нужные OAuth/Authorization протокольные пути к их владельцу и согласованные Hands MCP endpoints. **Не выполняет** JWT/C2/User/Project/AgentSession бизнес-проверки, не знает бизнес DTO и не поднимает другие сервисы. Авторизация остаётся у Identity/Authorization/целевого владельца/Hand; недоверенные X-* заголовки не дают полномочий. Не вводить обязательный Go/gRPC в MVP; используем внутренний REST/HTTP/FastMCP по назначению.
- Структура: services/infrastructure/<service>/, services/platform/<service>/, services/control-panel/{api,ui}/, services/hands/<hand>/; у каждого внутри свои Dockerfile, Compose, uv project/lock (для Python) или Bun lock, конфигурация и runtime. **Отдельная универсальная папка deploy/<service> не целевая.** Вложенные Git-репозитории НЕ обязательны: монорепозиторий с самостоятельными сервисными папками.
- Переиспользуемое — маленькие тематические shared/* (DTO, transport, util), только с ясным владельцем и потребителями; никакой общей глобальной ORM/бизнес-схемы. Допускается небольшое дублирование вместо обширных транзитивных зависимостей.
- Все документационные файлы живут ОТДЕЛЬНО от service folders: docs/services/infrastructure/<service>/, docs/services/platform/<service>/, docs/services/control-panel/{api,ui}/, docs/services/hands/<hand>/ в зеркальной структуре. README внутри сервисов не обязателен, документы не включать в runtime Watch.
- Coolify Watch Paths: папка собственного сервиса/** и несколько действительно используемых shared/<topic>/**. Изменение локального API -> обновляется только API; Identity/Hand -> только их приложение; изменение shared -> конкретные потребители. Нет обязательных AST per-file import/COPY/watch manifests. На время переноса **сохранить** старые deploy/<module> и текущие Coolify App UUID/alias, удалять их только после реального успешного переноса и возможности отката. Документированный путь к сервису и реально сохранённый Coolify Watch должны совпасть.

## D. PostgreSQL / Valkey / доверие внутренней сети

- Для текущего **Development** одобрена существующая общая PostgreSQL-учётная запись с повышенными правами и четыре отдельные логические базы владельцев. **Не вводить новые SQL-роли, базы или глобальные миграторы** в MVP ради принципиальной изоляции. Сервис выполняет только собственные owner Alembic revisions. Никогда не удалять уже существующие DB/volumes. Будущее разделение SQL прав — отдельная оптимизация после MVP.
- Реальный приоритет безопасности — изоляция MCP/Hands sandbox от внутренней сервисной сети, API, PostgreSQL, Valkey и сетевых секретов. Недоверенный код Hands/Terminal/Web не получает произвольный доступ к briareus-net или подсетям инфраструктуры. Проверить реальные Docker networks/namespace/FS/capabilities/egress; сетевые ограничения и внутреннюю проверку запросов выполнять у настоящего владельца, не на Gateway. Одного частного DNS/HTTP достаточно для транспорта, но **нельзя** считать его само по себе доказанной авторизацией: привилегированный запрос принимает лишь подтверждённый авторизованный actor/service context, а не чужой заголовок.
- Не вводить без доказательств каскад mTLS/Unix/JTI-проверок на каждом прокси-хопе. Защита изолированных исполнителей и разграничение доступа — важнее театра проверок. Внутренние креденшелы не должны попадать в песочницы, логи или trace.
- Valkey и кэш не являются отдельным обязательным gate MVP. Использовать для подтверждённых сценариев realtime/кэша, измерять необходимость; PostgreSQL остаётся durable источником прав/приглашений/JTI.

## E. Процесс разработки TRY, агентские роли и приёмка

- **TRY -> собственная сборка -> Dev deploy -> просмотр реального результата -> исправление, повторение.** Не устраивать согласования по каждому шагу, не блокировать сервисные PR предварительной приёмкой Оркестратора.
- По прямому указанию владельца **отключить написание и запуск тестовых наборов** на текущем этапе: unit/integration/e2e/smoke и необязательные CI test suites не разрабатывать, не требовать и не запускать ради формальной приёмки. Нативная сборка, компиляция/import, запуск приложения, реальные логи/HTTP после Dev-деплоя — не тестовая инфраструктура, они остаются необходимой проверкой «работает/сломалось». Уже настроенную защиту GitHub branch protection/required checks обходить запрещено; менять проверки можно только явным безопасным изменением конфигурации, не через --no-verify.
- Backend владеет Control Panel API, Identity/Authorization/Platform/Resources и контрактами этих сервисов; Runtime — Gateway, Hands и соответствующей инфраструктурной runtime-частью; Frontend — Control Panel UI. Для shared/* перед первым изменением назначить одного редактора через файл. Взаимодействие только через workspace tasks/progress/requests.
- Оркестратор проводит **послепубликационную независимую приёмку**, а не собирает/тестирует за агентов. Worker чаты кратким обычным текстом с эмодзи, без таблиц. Таблица с запускать/не запускать — только от Оркестратора владельцу.
- Любые действия с инфраструктурой: **только Briareus MCP, development и прямой allowlist приложений**. Другие проекты/environments, Shared Environments, глобальные страницы и plaintext секреты недоступны для чтения/изменения даже при наличии инструментов. Этот доступ не расширяется новым архитектурным решением.

## F. Критерии приёмки этапов

1. Identity самостоятельно генерирует ссылку в startup logs **только при count(superuser)<1**. Первый регистрирующийся получает superuser ровно один раз при конкурентных запросах. При наличии superuser нет системной ссылки, обычные invitations только от аутентифицированного superuser. Надёжный Identity signing key переживает рестарты.
2. Реальные /api/auth/* и /api/platform/me работают через Gateway -> Control Panel API -> Identity. Отклонённые 401/403/405 и отсутствие чужого API — не дефект. Полноценный первый пользователь подтверждён реальным разрешённым регистрационным сценарием, не одним healthcheck.
3. Любой изменённый сервис собирается из собственной папки и только своeго shared; его Dev Watch не пересобирает чужой runtime. Документация не триггерит сборку.
4. Ни одна сеть/песочница MCP не позволяет неавторизованному исполнителю лазить по внутренней инфраструктуре. Domain/Hand owner сам защищает привилегированные операции.
5. Каждый срез самостоятельно опубликован/развёрнут/исправлен агентом; приёмка Оркестратора по опубликованному SHA, без пересоздания всесистемного тестового контура.

**Историческое доказательство:** исходное ТЗ от 9 октября прямо допускало системную ссылку в startup logs и её последующий показ при каждом запуске. Решение от 12 октября подтверждает только начальный/восстановительный случай при отсутствии superuser и отменяет последующие системные ссылки. Старые противоположные тексты подлежат удалению из актуальных инструкций, а не новому override-заголовку.
