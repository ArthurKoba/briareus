# Deployment and Dev handoff

Status: execution order / cross-agent handoff
Date: 2026-10-03

This document prevents the frontend/backend/MCP refactor work from losing deployment assumptions while multiple agents work in parallel.

## Priority order

### P0 — Coolify deployment contract

Complete and merge the Coolify contract before beginning the large DDD/upstream-first implementation.

Acceptance:

- externally-issued OAuth values are explicit required `${VAR:?}` inputs;
- internal random bootstrap secrets are generated by Coolify and remain stable between deployments;
- existing production encrypted state preserves its original encryption/signing secrets during migration;
- public gateway URL/host/origin can be generated by Coolify or explicitly overridden;
- timezone/locale and internal MCP locations are explicit deployment inputs with portable defaults;
- browser identity settings are independent from backend machine timezone/locale;
- environment-variable values are never exposed through the Observability MCP;
- safe Coolify inventory exposes application/server/resource identity, source branch/compose location and env key names/flags only;
- full CI passes before production rollout;
- production live acceptance confirms generated/source metadata and redaction.

### P0.5 — local-first GitHub workflow

Before parallel refactor work expands again:

- keep local-first guidance enabled in Admin API application settings;
- substantial code changes happen in persistent local workspaces;
- agents may make local commits freely, then squash/reorder before publication when useful;
- publish the validated branch once through authenticated Git transport;
- if Git transport is unavailable, use one batched `github_agent_commit_files` fallback instead of repeated file commits;
- create the PR only after the branch is ready for integration;
- use GitHub REST tools primarily for PR/review/issues/checks/control-plane work;
- remote source/history mutations can be disabled from Admin API application settings after the local Git transport is accepted;

### P1 — synchronize `main` into `dev`

`dev` contains frontend/platform work and is intentionally not reset to `main`.

Current observed relationship before this handoff: `dev` and `main` are diverged. Synchronization must be a normal merge of accepted `main` into `dev`, resolving conflicts without dropping frontend commits. No force-reset/repoint of `dev`.

Do this only after P0 is merged so Dev starts from the final deployment contract.

### P2 — isolated Dev Coolify resource

Create a separate Coolify Git-backed Docker Compose resource on branch `dev`.

It must not share production mutable state:

- separate named volumes;
- separate generated Admin API/auth secrets;
- separate Valkey;
- separate browser profile;
- separate public Dev domain;
- separate GitHub OAuth callback/application identity;
- `OTEL_ENVIRONMENT=development`;
- isolated Ghidra worker pool/backend for destructive analysis tests.

The Dev resource may point to common read-only external providers only when doing so cannot mutate production state.

### P3 — browser platform follow-up

Browser work follows the deployment/Dev foundation, not before it.

Keep the existing persistent real Chromium + CDP + official DevTools MCP model. Product/runtime settings to expose cleanly:

- viewport width/height;
- browser timezone;
- locale / Accept-Language / POSIX locale;
- display/headless/desktop mode where supported;
- future named isolated browser profiles/contexts for testing multiple accounts/devices against the same application;
- lifecycle controls for create/open/clean/delete an isolated profile;
- operator-visible profile identity and tab list;
- shared human/agent access controls per profile/tab.

For multi-account application testing, prefer genuinely isolated Chromium profiles/contexts with independent cookies/storage. Do not add anti-bot fingerprint spoofing or site-control bypass logic; use normal Chromium/device/context configuration.

### P4 — backend clean architecture + upstream-first MCP work

Only after Dev is healthy and isolated:

- generic account-scoped upstream MCP proxy;
- SQL/Valkey/event/OTLP control-plane phases;
- frontend `/api/v1` OpenAPI migration;
- realtime WebSocket/event bus;
- frontend telemetry relay;
- upstream SigNoz/Coolify/Playwright/GitLab/GitHub migrations.

Authorities:

- `docs/refactoring/mcp-upstream-roadmap.md`
- `docs/refactoring/backend-control-plane-roadmap.md`

## Coolify MCP / Observability inventory policy

Agents need enough infrastructure metadata to reason about deployment topology without gaining a secret-reading endpoint.

Allowed:

- Coolify application UUID/name/status;
- Git repository and branch;
- build pack;
- Dockerfile/Compose source locations;
- safe build/deployment flags;
- server UUID/name/role/proxy type/status-like metadata;
- resource UUID/name/type/status;
- environment variable **keys** and non-secret scope/flag metadata;
- deployment status/commit/timestamps.

Forbidden:

- environment `value` / `real_value`;
- secret comments or one-time secret content;
- API tokens;
- raw rendered Compose/configuration bodies;
- nested proxy/Sentinel configuration;
- authorization headers;
- arbitrary nested provider payloads that may contain credentials.

For a Git-backed Compose application, use Coolify metadata to discover repository/branch/compose path, then read the source Compose file through the GitHub/GitLab MCP. This keeps source authority and secret boundaries clear.

## Production preservation rule

No Dev or refactor operation may intentionally use production mutable volumes, browser profiles, Ghidra worker sessions or auth stores as a test target.

Production remains `main`. Dev integration happens on `dev`. Changes graduate from Dev only after the relevant source/build/runtime acceptance level is demonstrated.
