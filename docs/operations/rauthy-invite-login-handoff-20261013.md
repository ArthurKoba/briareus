## Owner decisions — binding acceptance

1. **Closed enrollment, no public self-registration.** An unknown visitor must not create a Briareus/Rauthy account or obtain access by navigating directly to either the Briareus UI/API or an upstream Rauthy route. Only an administrator-issued, scoped, expiring, one-use invitation/registration key (or an explicitly approved equivalent operator action) may permit enrollment. Invitation creation, redemption, cancellation, expiry, replay denial and audit must have real authority; no publicly reusable registration secret. Verify the supported upstream Rauthy enrollment/self-registration behavior before selecting the exact implementation; do not invent provider APIs or assume registration is already disabled.
2. **Existing Rauthy accounts sign in with their own credentials.** Human admins and users use real Rauthy OAuth2/OIDC authorization code + PKCE, with upstream password/MFA rules. No second Briareus password store. An OAuth public `client_id` is **not** an invitation key; a protected `RAUTHY_ADMIN_API_KEY` is a service-to-service administration credential, **not** a user password or browser token. Never expose it or any protected Valkey credential to the browser/logs.
3. **Authentication is not authorization.** A verified Rauthy `sub` proves external identity only. Platform Control must bind it to a real Briareus User, Team/Project membership and operator role from authoritative state. A Rauthy admin role, account creation or invitation does not automatically convey Briareus management or MCP privileges.
4. **Default-deny MCP resources.** Authorization owns active AgentSession grants/approval/revocation and Cedar decisions; Gateway admits only verified connections and remains transport-oriented; each Hand checks the exact current resource/effect. Uninvited, unknown, unauthenticated and ungranted actors cannot consume Terminal, Web, Files or other Hands. No fabricated allow, user or service token.
5. **Controlled legacy retirement.** The current temporary legacy Identity login/register form may return 503 and is not the target login. Make Rauthy the primary coherent UI experience, but preserve old Identity/data/volumes and rollback until the real Rauthy login, Platform binding, invite restrictions, deny/revoke and independent service restart acceptance are evidenced. Avoid treating a removed button as a completed security migration.
